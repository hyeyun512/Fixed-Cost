# FC.2 — edit 파일에 Supabase 리소스배부율 반영

## 이 스킬이 하는 일

`edit_{월}월.xlsx`(fc-1로 만든 파일, 또는 "edit" 시트에 `배부기준`/`Amount(KRW)` 열이 있는 동일 구조의
파일)를 받아서, `배부기준` 열의 값을 key로 Supabase의 리소스배부율 테이블을 조회하고, 그 오른쪽에
배부율(%)·배부후금액(KRW) 열을 추가한 `edit_{월}월(배부ver).xlsx` 파일을 새로 만든다.

**원본 파일(`edit_{월}월.xlsx`)은 절대 건드리지 않는다.** 항상 복사본을 새로 만들어 작업한다.

## Supabase 테이블 구조 (2026-07 기준)

리소스배부율은 분기별로 별도 테이블(`allocation_rate_2026_q1`, `allocation_rate_2026_q2` 등)로
나뉘어 있었으나, 하나의 `allocation_rate` 테이블로 통합되었다. 분기 구분은 맨 앞의 `quarter` 열
(예: `'2026-Q1'`, `'2026-Q2'`, 형식은 `'{연도}-Q{분기}'`)로 한다. 나머지 컬럼(`type`, `division`,
`basis`, `stb`, `mobility`, `evcs_domestic`, `evcs_overseas`, `humax_common`, `building`,
`h_mobility`, `h_ev`, `hiparking`, `peoplecar`, `winercom`, `holdings`, `h_networks`, `total`,
`update_flag`, `note`)는 예전 분기별 테이블과 동일하다.

## 사용자가 확정한 사양 (매번 그대로 적용)

이 사양은 실제 사용자와 왕복하며 확정한 내용이다. 다음번에 다시 물어볼 필요 없이 아래 규칙을 기본값으로
적용하되, 애매한 부분(배부율표에 없는 배부기준 등)이 나오면 사용자에게 알린다.

1. **파일명**: 입력 파일이 `edit_{N}월.xlsx`라면 출력은 `edit_{N}월(배부ver).xlsx`. (단순히
   `edit(배부ver).xlsx`처럼 월 정보를 빼먹지 않는다 — 처음에 이걸 빼먹어서 사용자가 정정한 적이 있다.)
2. **분기 매핑**: 5월 → 2분기(Q2), 즉 1~3월=Q1, 4~6월=Q2, 7~9월=Q3, 10~12월=Q4. 연도는 파일명/데이터의
   Posting Date에서 판단하고, 명시적으로 다른 연도라고 하지 않는 한 해당 연도를 그대로 쓴다. 이 연도/분기를
   `allocation_rate` 테이블의 `quarter` 열 값(`'{연도}-Q{분기}'`)으로 변환해 조회한다.
3. **열 순서**: `배부기준` 열 바로 오른쪽부터 순서대로 —
   `STB(%)`, `Mobility(%)`, `EVCS(국내)(%)`, `EVCS(해외)(%)`, `Humax(공통)(%)`, `건물(%)`,
   `H.Mobility(%)`, `H.EV(%)`, `하이파킹(%)`, `피플카(%)`, `위너콤(%)`, `홀딩스(%)`, `H.Networks(%)`,
   `합계(%)`, 그다음 `STB(KRW)` ~ `H.Networks(KRW)`(같은 순서), 마지막으로 `합계(KRW)`.
   헤더에는 "배부율"이나 "배부후금액"이라는 단어를 쓰지 않는다 — `(%)`/`(KRW)` 접미사만으로 의미가
   전달된다는 게 사용자 판단이다.
4. **배부율(%) 열은 값이 아니라 수식으로 채운다.** 워크북에 함께 추가하는 "배부율(Supabase)" 참고
   시트(12번 규칙)를 대상으로 `=IFERROR(VLOOKUP(그 행의 배부기준 셀, '배부율(Supabase)'!$A$2:$O$마지막행,
   해당 구분의 열 번호, FALSE), 0)` 형태의 VLOOKUP 수식을 쓴다. 배부기준 값이 배부율표에 없어 VLOOKUP이
   매칭에 실패하면 IFERROR가 **0**(0%)을 반환하도록 한다 — 텍스트나 에러가 아니라 항상 숫자 0이어야
   `합계(%)` 열 SUM과 배부후금액 수식(5번)이 깨지지 않는다. (한때 매칭 실패시 "확인요망" 텍스트를
   표시하도록 만든 적이 있었는데, 사용자가 다시 0%로 되돌려 달라고 정정했다 — 텍스트를 쓰면 안 된다.)
   `합계(%)` 열만 `=SUM(해당 행의 13개 배부율)` 수식이다.
5. **배부후금액(KRW) 열은 반드시 수식**: `=Amount(KRW)열의 같은 행 * 그 구분의 배부율(%)열`(평범한
   곱셈, IFERROR로 감쌀 필요 없음 — 4번 규칙 덕분에 배부율(%) 열이 항상 숫자이므로 곱셈이 에러를 내지
   않는다). `합계(KRW)` 열도 `=SUM(13개 배부후금액 열)` 수식.
6. **금액 서식 통일**: 배부후금액(KRW) 열과 합계(KRW) 열의 숫자 서식은 원본 `Amount(KRW)` 열과 동일하게
   맞춘다 (보통 `#,##0;[Red]-#,##0` — 음수는 빨간색). 1행(합계 행)에도 같은 서식을 적용한다.
7. **1행 합계**: 새로 추가한 13개 배부후금액 열 + 합계(KRW) 열도 기존 관례(`Amount(KRW)` 등)를 따라
   `=SUBTOTAL(109, ...)` 수식으로 채운다 — SUM이 아니라 SUBTOTAL이어야 자동 필터로 화면에 보이는 행만
   합산된다.
8. **헤더 색**: 배부율(%) 계열 헤더(13개 + 합계(%))는 옅은 파란색(`E8F0FE`), 배부후금액(KRW) 계열 헤더
   (13개 + 합계(KRW))는 옅은 주황색(`FFF6E0`). 볼드 처리한다 (이 열들은 fc-1의 "새로 추가한 열은 진한
   회색, 볼드 없음" 규칙과는 별개의 새 규칙이므로 볼드를 써도 된다 — 사용자가 이 부분엔 볼드 금지를
   요구하지 않았다).
9. **합계(%) 열 조건부 서식** (제일 까다로운 부분이니 정확히 지킬 것):
   - 값이 **100%**면 → 채우기 없음
   - 값이 **0%인데 배부기준이 "실적 제외"**면 → 채우기 없음 (배부율표에서 실적 제외는 원래 TOTAL=0으로
     설계되어 있어서 정상이다)
   - 그 외 (0%인데 실적 제외가 아니거나, 0%도 100%도 아닌 애매한 값) → `#FDE9D9`로 채우기
   - 이 조건은 하나의 수식으로 표현: `AND(ABS(셀-1)>0.001, NOT(AND(셀=0, 배부기준셀="실적 제외")))`
   - **주의**: PatternFill의 fgColor를 `00xxxxxx`(알파 00 = 완전 투명)로 저장하면 Excel에서 색이 전혀
     안 보이는 버그가 있었다. 반드시 `FFxxxxxx`(알파 FF = 불투명)로 지정할 것. `scripts/apply_allocation.py`는
     이미 이렇게 처리되어 있다.
   - 채우기 색과 무관하게 셀 테두리(눈금선처럼 보이는 옅은 회색 `D9D9D9` thin border)를 합계(%) 열
     전체에 넣는다 — 안 그러면 조건부 서식이 적용된 셀만 눈금선이 사라져 보이는 문제가 있었다.
10. **자동 필터**: 기존 자동 필터 범위를 새로 추가한 마지막 열(합계(KRW))까지 확장한다.
11. **배부율표에 없는 배부기준 처리**: `배부기준` 열 값이 Supabase 배부율표(basis 컬럼)에 없으면
    "배부율(Supabase)" 참고 시트에도 그 배부기준 행을 추가하지 않는다 — VLOOKUP이 자연스럽게 매칭
    실패하고, 4번 규칙의 IFERROR가 **0%**를 반환한다 (배부후금액도 자동으로 0원이 되고, 합계(%) 열은
    0%라서 위 9번 규칙에 따라 `#FDE9D9`로 강조된다). 이 값들은 "검증" 시트에 목록으로 정리해서
    사용자에게 건별 확인이 필요하다고 알린다. (실제로 겪은 사례: "별도배부율"이라는 포괄적인 값이
    배부기준에 들어있었는데, Supabase에는 그보다 세부적인 key(`EVCS(국내/해외)`, `EVCS(국내30/해외70)`
    등)만 있어서 정확히 매칭되지 않았다. 사용자에게 확인한 결과 0%로 처리하기로 했다.)
12. **참고용 배부율표 시트**: 실제 적용에 사용한 배부율표를 "배부율(Supabase)"라는 이름의 시트로 워크북에
    같이 넣는다 (배부기준 값 → 13개 배부율 → TOTAL, 헤더 포함 A~O열). 나중에 검산하거나 배부기준별
    배부율을 확인할 때 바로 볼 수 있게 하기 위함이기도 하지만, 4번 규칙의 VLOOKUP 수식이 참조하는
    실제 lookup 테이블이기도 하다 — 이 시트를 지우거나 이름을 바꾸면 edit 시트의 배부율(%) 수식이
    전부 깨진다.
13. **검증 시트**: 기존에 "검증" 시트가 있으면(fc-1이 만든 raw 결합 검증 내용) 그 아래에 이어서, 없으면
    새로 만들어서, 배부 매칭 결과 요약(매칭 성공 건수 / 실적 제외 건수 / 배부율표 미매칭 건수와 목록)을
    표로 추가한다.

## 실행 순서

1. **입력 파일 확인**: 사용자가 첨부한 edit 파일을 읽고 "edit" 시트에 `배부기준`, `Amount(KRW)` 헤더가
   있는지 확인한다. 없으면 이 스킬 대상이 아니므로 사용자에게 어떤 파일인지 확인한다.
2. **대상 월 파악**: 파일명(`edit_5월.xlsx` 등) 또는 데이터의 Posting Date에서 대상 연/월을 파악하고,
   2번 규칙(분기 매핑)에 따라 `{연도}-Q{분기}` 형태의 quarter 값을 만든다 (예: 5월 → `2026-Q2`).
3. **Supabase 배부율표 조회**: Supabase MCP로 다음을 수행한다.
   - `list_tables`로 `allocation_rate` 테이블이 있는지 확인한다 (없으면 사용자에게 테이블 구조가 바뀌었는지
     확인한다).
   - `execute_sql`로 `SELECT * FROM allocation_rate WHERE quarter = '{연도}-Q{분기}' ORDER BY id`를
     실행해 해당 분기 행만 가져온다.
   - 결과를 JSON 배열로 저장한다 (컬럼: `type`, `division`, `basis`, `stb`, `mobility`, `evcs_domestic`,
     `evcs_overseas`, `humax_common`, `building`, `h_mobility`, `h_ev`, `hiparking`, `peoplecar`,
     `winercom`, `holdings`, `h_networks`, `total` — `quarter`/`id`/`update_flag`/`note`/`created_at`
     같은 다른 컬럼이 JSON에 같이 들어있어도 무방하다, 스크립트가 필요한 키만 읽는다). 이 JSON을
     `scripts/apply_allocation.py`의 두 번째 인자로 넘긴다.
4. **스크립트 실행**:
   ```
   python scripts/apply_allocation.py <edit_{월}월.xlsx 경로> <supabase_rates.json 경로> <edit_{월}월(배부ver).xlsx 출력 경로>
   ```
   이 스크립트가 위 1~13번 사양을 전부 자동으로 처리한다. 실행이 끝나면 매칭되지 않은 배부기준 목록을
   콘솔에 출력해준다.
5. **검증**: `scripts/verify.py <output.xlsx>`를 실행해 다음을 확인한다 (아래 "검증 방법" 참고).
6. **결과 전달**: 원본 파일이 있던 위치(사용자 작업 폴더)에 `edit_{월}월(배부ver).xlsx`로 저장하고
   `present_files`로 사용자에게 보여준다. 미매칭 배부기준이 있으면 어떤 값들인지, 어떻게 처리했는지
   (0% 적용) 짧게 알린다.

## 검증 방법

openpyxl로 저장한 파일은 수식이 계산된 값을 캐시하지 않으므로, 셀 값이 필요하면 LibreOffice headless로
재계산 후 읽는다:

```
libreoffice --headless --convert-to xlsx --outdir <임시폴더> <output.xlsx>
```

그 다음 재계산된 파일에서 `SUBTOTAL(109, Amount(KRW))`(1행)과 `SUBTOTAL(109, 합계(KRW))`(1행)을 비교해
차이가 있으면, 그 차이가 전부 "실적 제외" 행 + 배부율표 미매칭(0% 처리) 행에서만 발생하는지 확인한다
(`scripts/verify.py`가 이 로직을 그대로 구현해 둔 스크립트다 — 배부기준별로 그룹핑해서 Amount(KRW) 합계와
배부후금액 합계 차이를 리포트한다). 그 외 배부기준에서 차이가 나면 배부율표 반영이나 수식에 문제가 있는
것이므로 원인을 찾아야 한다.

## 알아두면 좋은 것

- 이 스크립트는 입력 파일의 "edit" 시트에서 헤더 텍스트(`배부기준`, `Amount(KRW)`)로 열 위치를 찾기
  때문에, fc-1이 만든 파일이 아니어도 이 두 헤더만 있으면 동작한다. 다만 열 순서나 추가 열 유무에 따라
  최종 컬럼 알파벳(AI, AW, BK 등)은 파일마다 달라질 수 있다 — 스크립트가 이를 자동으로 계산하므로
  하드코딩된 열 문자에 의존하지 않는다.
- 원본 edit 파일의 `Amount(KRW)` 열이 수식(`=X*Y` 등)인 경우, 그 값 자체는 건드리지 않고 그대로
  참조만 한다.
- `scripts/apply_allocation.py` 자체는 테이블 이름이나 quarter 개념을 전혀 모른다 — Supabase에서 가져온
  행 목록(JSON)만 받아서 `basis` 컬럼을 key로 쓴다. 따라서 조회 SQL(3번 단계)에서 올바른 분기 행만
  걸러서 넘기기만 하면 되고, Supabase 테이블/컬럼 구조가 또 바뀌지 않는 한 스크립트 자체는 수정할
  필요가 없다.
- Supabase 프로젝트/테이블 구조가 또 바뀌면(예: 컬럼명이 달라지거나 컬럼이 추가/삭제되면) `build_rates_dict()`
  함수와 `DIVISIONS` 리스트를 업데이트해야 한다.

## 이 스킬 자체를 업데이트할 때

사용자가 "fc-2 스킬 업데이트해줘" 같이 이 스킬 자체의 수정을 요청하면, `mcp__cowork__save_skill` 도구를
`name: "fc-2"`, `overwrite: true`로 호출해 SKILL.md 내용을 갱신한다. `scripts/` 폴더의 스크립트 파일은
save_skill로 건드릴 수 없고 그대로 유지되므로, 스크립트 자체를 바꿔야 하면 skill-creator 스킬을 사용해
새 `.skill` 패키지를 만들어 사용자에게 전달하고 설치(업데이트)하도록 안내한다.
